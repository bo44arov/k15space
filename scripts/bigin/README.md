# BiginSync.gs — функціональний опис для AI-агента

Документ описує фактичну реалізацію сусіднього [BiginSync.gs](./BiginSync.gs), а не бажану бізнес-логіку чи стан живого Apps Script. Оновлено 20.11.2026: новий порядок годин і ручні додаткові години. Якщо код зміниться, актуалізуйте цей документ. Наявність файлу на GitHub не підтверджує, що саме ця версія встановлена в Google Apps Script.

## 1. Призначення та межі

Скрипт Google Apps Script читає події Zoho Bigin і записує їх у Google Sheets. Має два незалежні режими:

| Режим | Функція | Результат |
| --- | --- | --- |
| Базова вигрузка | `syncBiginEvents()` | Повністю оновлює A:E вкладки «События Bigin», включно з очищенням залишкових старих значень |
| Облік заходів | `syncBiginReport()` | Додає нові події, прив'язує наявні рядки до ID, створює місячні блоки й сортує рядки всередині блоків |
| Попередній перегляд обліку | `previewBiginReportSync()` | Виконує читання, перевірки й планування обліку, виводить лічильники без запису в таблицю |

Напрямок даних: Bigin → Google Sheets. Скрипт не змінює CRM, не бронює студії, не надсилає повідомлення та не змінює сайт. Він не розраховує зарплату або об'єднані години присутності адміністратора.

Для режиму обліку «тільки додавання» означає відсутність оновлення значень уже прив'язаних подій. Це не означає запис лише в кінець аркуша: скрипт вставляє рядки всередину таблиці, додає заголовки місяців, записує службові ID й переміщує цілі рядки.

## 2. Середовище та залежності

Виконується в Google Apps Script із підтримкою сучасного JavaScript: `Map`, `Set`, spread, optional chaining. Використовує:

- `PropertiesService`: налаштування та OAuth refresh token.
- `UrlFetchApp`: HTTPS-запити до Zoho.
- `SpreadsheetApp`: читання, вставлення, форматування та переміщення рядків.
- `LockService`: блокування паралельних запусків у межах одного проєкту.
- `ScriptApp`: погодинні тригери.
- `Utilities.formatDate`: форматування дат.

Рекомендований спосіб розміщення — окремий закритий проєкт Apps Script. Секрети задаються через Script Properties. У коді немає ID конкретної таблиці, OAuth-ключів або даних клієнтів.

Поточні адреси зафіксовані в коді:

| Константа / ресурс | Значення |
| --- | --- |
| `BIGIN_ACCOUNTS` | `https://accounts.zoho.com/oauth/v2/token` |
| `BIGIN_EVENTS` | `https://www.zohoapis.com/bigin/v2/Events` |
| Contacts | Отримується заміною кінцевого `Events` на `Contacts` |
| `BIGIN_KYIV` | `Europe/Kyiv` |

Інші дата-центри Zoho автоматично не визначаються. OAuth scopes, manifest Apps Script і процес створення OAuth-клієнта у файлі не задані; не приписуйте їм значень, яких немає в реалізації.

## 3. Script Properties

Усі прочитані обов'язкові значення обрізаються через `trim()`; відсутність або порожнє значення спричиняє помилку.

| Властивість | Призначення |
| --- | --- |
| `BIGIN_SHEET_ID` | ID Google Spreadsheet для обох режимів |
| `BIGIN_CLIENT_ID` | OAuth client ID Zoho |
| `BIGIN_CLIENT_SECRET` | OAuth client secret Zoho |
| `BIGIN_REFRESH_TOKEN` | Refresh token для регулярних запусків |
| `BIGIN_AUTH_CODE` | Одноразовий код лише для `exchangeBiginCode()` |
| `BIGIN_REPORT_TAB` | Необов'язкова назва вкладки обліку; стандартно «Заходи — облік» |
| `BIGIN_REPORT_VERIFIED` | Службова позначка `<sheetId>:<reportTab>`, яку скрипт записує після успішної синхронізації обліку |

Назва «Звіт. Івенти-бігін» не є стандартною в цій версії: для неї потрібно встановити `BIGIN_REPORT_TAB`.

`BIGIN_REPORT_VERIFIED` не є підтвердженням ручного перегляду людиною. Вона встановлюється автоматично після запису й сортування, а інсталятор тригера лише перевіряє її відповідність поточним ID таблиці та назві вкладки.

## 4. OAuth та HTTP

`exchangeBiginCode()` надсилає POST із `grant_type=authorization_code`, кодом і client credentials. Якщо у відповіді є refresh token, зберігає його в `BIGIN_REFRESH_TOKEN` та видаляє `BIGIN_AUTH_CODE`. Відсутність refresh token — помилка. Обмін коду також проходить перевірку на наявність access token.

Кожна синхронізація заново отримує access token через `grant_type=refresh_token`. Access token не кешується й не записується у властивості.

`biginRequest_()`:

- викликає `UrlFetchApp.fetch` із `followRedirects: false` і `muteHttpExceptions: true`;
- для HTTP 204 повертає `null`;
- приймає лише HTTP 200 як звичайну успішну відповідь;
- для інших статусів кидає помилку з HTTP-кодом;
- для 200 розбирає JSON; помилки JSON не перехоплюються.

Retry, backoff і спеціальна обробка 429 відсутні. Відповідь OAuth без access token перетворюється на помилку; явно розпізнаються `invalid_client`, `invalid_client_secret`, `invalid_code`, `invalid_grant`, інші випадки описуються як відсутність access token. Сирі тіла помилок і секрети навмисно не виводяться цим кодом.

## 5. Читання Bigin і пагінація

`readBiginModule_(endpoint, fields, accessToken, wantedIds)` — спільний читач Events і Contacts:

1. Передає заголовок `Authorization: Zoho-oauthtoken <accessToken>`.
2. Запитує `per_page=200`, `sort_by=id`, `sort_order=asc` і перелік полів.
3. Починає з `page=1`, переходить до сторінки 10, а потім використовує `info.next_page_token`.
4. Перевіряє, що `data` — масив, а `info.more_records` — boolean.
5. Вимагає для кожного запису рядковий числовий `id`, що відповідає `/^\d+$/`.
6. Збирає записи у `Map` за `id`: повторний ID замінює попередній запис.
7. Завершує роботу після HTTP 204, `more_records=false` або знаходження всіх `wantedIds`.
8. Відсутній або повторений токен наступної сторінки спричиняє помилку.

`wantedIds` — локальний фільтр результатів, а не параметр API. Для контактів скрипт може переглядати весь доступний модуль, поки не знайде всі потрібні ID або не закінчаться сторінки. Якщо контакт не знайдено, це враховується в журналі, але саме по собі не зупиняє імпорт.

ID залишаються рядками, щоб не втратити точність великих чисел.

## 6. Базова вкладка «События Bigin»

Запитувані поля Events: `Start_DateTime,End_DateTime,All_day,$event_cancelled`. Фільтра за `$u_id` або датою немає.

| Стовпець | Заголовок | Значення |
| --- | --- | --- |
| A | ID события | Рядковий ID Bigin |
| B | Начало · Киев | Початок у `Europe/Kyiv`, формат `yyyy-MM-dd HH:mm` |
| C | Конец · Киев | Кінець у тому самому форматі |
| D | Статус | Статус за правилами нижче |
| E | Длительность, ч | Різниця кінця й початку в годинах для валідних подій не на весь день |

Час валідний, якщо обидві дати існують, розбираються і кінець не раніше початку. Статуси мають пріоритет: `$event_cancelled === true` → «Отменено»; інакше `All_day` → «Весь день»; інакше валідний час → «В календаре»; решта → «Проверить время».

За невалідного часу B і C порожні. Тривалість для подій на весь день порожня; для скасованої події з валідним часом і без All_day тривалість усе одно обчислюється.

Перед записом у непорожню вкладку перевіряються точні п'ять заголовків. Відмінність зупиняє виконання. Скрипт переписує A:E до більшого з поточного й нового числа рядків, доповнюючи порожніми рядками старий хвіст. Самі рядки аркуша не видаляються; стовпці правіше E не переписуються, але їхні дані не мають гарантованого зв'язку з оновленими подіями.

A:C отримують текстовий формат. Лише при створенні нової вкладки заморожується перший рядок, оформлюється заголовок і встановлюється ширина п'яти стовпців 175.

## 7. Структура вкладки обліку

Перший рядок містить точні заголовки A:P. A:O перевіряються обов'язково; P може бути порожнім для первинної прив'язки, але зайнятий іншим заголовком або даними без заголовка P блокує імпорт.

| Колонка | Точний заголовок | Джерело / правило нового рядка |
| --- | --- | --- |
| A | Дата | Дата початку події за Києвом |
| B | Створено | Дата створення події за Києвом, без часу |
| C | Зала | Назва містить `AURA` без урахування регістру → `Aura`; інакше `Sakura` |
| D | Захід | `Event_Title` або порожній рядок |
| E | Ім'я | `Related_To.name` лише для зв'язку з Contacts |
| F | Номер тел | `Contact.Phone` або порожній рядок; текстовий формат |
| G | Посилання на інсту | Нормалізоване посилання Instagram |
| H | Інста | `@handle` або початкове некоректне значення |
| I | Години | Київський інтервал `HH:mm–HH:mm` |
| J | Кількість годин | Різниця timestamps у годинах |
| K | Додатокві години | Ручне число після заходу, нові рядки порожні |
| L | Сумма | Формула суми основних і додаткових годин |
| M | Примітки | Ручне заповнення |
| N | дод послуги | Ручне заповнення |
| O | Інформація | Description |
| P | Bigin Event ID | Прихований рядковий ID |

A і B записуються як числові серійні дати Sheets із форматом `dd.mm.yyyy`: `Date.UTC(year, month - 1, day) / 86400000 + 25569`.

Формула L для рядка n:

```text
=ROUND((Jn+Kn)*IF(Bn>DATE(2026,9,1),1300,800),2)
```

Наприклад, для рядка 5: `=ROUND((J5+K5)*IF(B5>DATE(2026,9,1),1300,800),2)`.

Критична деталь: тариф залежить від **дати створення B**, а не дати заходу A. Порівняння строго більше: 01.09.2026 дає 800, дата пізніше — 1300. Час створення відкинутий до порівняння. Це опис чинного коду, не підтвердження актуального бізнес-тарифу. Ручні додаткові години K враховуються за тим самим тарифом. Порожня K у додаванні дорівнює нулю; можна вводити дробові години (наприклад, 0,5 у відповідній локалі таблиці). Нечисловий текст може спричинити помилку формули. Додаткові послуги, студія й знижки не враховуються.

## 8. Відбір і перетворення подій обліку

Запитувані поля: `Event_Title,Start_DateTime,End_DateTime,Created_Time,Description,Related_To,$related_module,$u_id`.

Після завантаження всіх сторінок проходять лише події, чий обрізаний `$u_id` відповідає GUID-подібному формату `8-4-4-4-12` hex-символів без перевірки версії UUID.

Дедуплікація виконується за `id`, а не за `$u_id`. Два різні ID з однаковим GUID можуть потрапити в облік як різні події. Події без валідного GUID пропускаються без окремого журналу кожної пропущеної події.

Далі відкидаються вже наявні у стовпці P ID. Контакти завантажуються лише для ще не прив'язаних подій, лише коли `$related_module === 'Contacts'`; використовується `Related_To.id`. Ім'я береться зі зв'язку події, телефон та Instagram — із запису Contacts.

Для кожної нової події початок, кінець і Created_Time мають бути валідними, а кінець — не раніше початку. Одна невалідна нова подія перериває весь запуск до запису. Уже прив'язані події не проходять повторне перетворення.

Тривалість рахується за timestamps; інтервал I не містить дат, тому сам по собі не пояснює перехід через північ. Скасування та All_day у режимі обліку не запитуються й окремо не обробляються.

Instagram: обрізає пробіли й початковий `@`, прибирає префікс instagram.com із можливими http(s), www або m, query/hash і кінцевий слеш. Якщо результат відповідає `[A-Za-z0-9_.]{1,30}`, створює `https://www.instagram.com/<handle>/` і `@<handle>`. Інакше G порожня, H містить початкове обрізане значення. Перевірки існування акаунта немає.

## 9. Ідентичність рядків і первинна прив'язка

`planBiginReport_()` спочатку перевіряє всі наявні ID в P: вони мають бути числовими рядками й унікальними. Некоректний або дубльований ID зупиняє запуск.

Для кожного непорожнього рядка без ID, який не є заголовком місяця, обов'язково шукається відповідна ще не прив'язана подія за ключем:

```text
JSON.stringify([Дата, Створено, Захід, Години].map(trim))
```

Ключ використовує відображувані значення A, B, D, I; регістр назви, пунктуація і формат інтервалу мають збігатися. Якщо кандидатів кілька, додатково порівнюються ім'я E й телефон F. Має залишитися рівно один кандидат, інакше виконання зупиняється. Визначений ID записується тільки в P; бізнес-дані старого рядка не переписуються.

Це суттєве обмеження для ручних записів: довільний непорожній ручний рядок без ID не ігнорується, а може заблокувати синхронізацію. Порожні рядки та розпізнані місячні заголовки пропускаються. Не вигадуйте фіктивні ID для обходу перевірки.

Нові рядки — події, ID яких немає ані в наявних прив'язках, ані серед щойно зіставлених рядків.

Уже імпортована подія не оновлюється при зміні часу, назви, контакту або Description в CRM. Видалені з CRM події не видаляються з таблиці.

## 10. Місячні блоки, запис і сортування

Місячний заголовок — назва місяця ВЕЛИКИМИ українськими літерами, пробіл і чотири цифри року, наприклад «ЛИСТОПАД 2026». Під час планування решта клітинок A:P такого рядка має бути порожня. Список назв задається `BIGIN_MONTHS`.

`planBiginMonthWrites_()`:

- визначає місяць із заголовків і дат A у точному форматі `dd.MM.yyyy`;
- перевіряє зростання місяців і відсутність повторних заголовків;
- групує нові події за датою заходу A;
- додає відсутні місячні заголовки;
- планує вставки в кінці відповідного місяця, перед наступним блоком;
- повертає операції від нижніх рядків до верхніх, щоб зберегти індекси.

Нові рядки в групі попередньо сортуються за датою без часу. Заголовки місяців об'єднуються в A:O, центруються, виділяються жирним і товстою чорною рамкою.

`writeBiginReport_()` перевіряє незмінність lastRow; за потреби додає P, заголовки та приховує P. Перший рядок заморожується лише при початковому створенні структури. Первинні прив'язки записуються послідовними групами ID.

Дані нового рядка записуються в A:P. У текстах із primary-полів і Description початкові `=`, `+`, `-`, `@` або апостроф екрануються додатковим апострофом, щоб не виконувати їх як формули. L є навмисно сформованою формулою.

Після запису й flush виконується `sortBiginMonthRows_()`:

- читає фактичні й відображувані значення A;
- для Date використовує часовий пояс самої таблиці;
- розпізнає дати з одним або двома розрядами дня та місяця;
- сортує за календарною датою всередині діапазону після останнього заголовка;
- переміщує **весь рядок** через `sheet.moveRows`, разом із формулами, ручними колонками й ID;
- зберігає відносний порядок однакових дат; час початку не є ключем;
- пропускає рядки без розпізнаної дати як активні елементи сортування, але їхня позиція може зміститися через переміщення інших рядків.

Цей сортувальник не виправляє неправильний місяць розміщення рядка. Попередня перевірка порядку місяців може зупинити запуск раніше. Виконується і коли нових подій немає. Preview не запускає саме переміщення й не прогнозує його кількість.

## 11. Конкурентність і часткові зміни

Обидві синхронізації та обидва інсталятори тригерів використовують script lock з очікуванням 10 000 мс та звільняють його у finally. Preview також захоплює цей lock. Обмін auth code блокування не має.

Lock захищає запуски цього проєкту, але не ручні правки користувача й не інші проєкти Apps Script.

Для обліку запам'ятовується lastRow і перевіряється перед записом. Якщо заплановані первинні прив'язки, додатково повторно порівнюються відображувані значення наявних рядків. Якщо прив'язок немає, повне повторне порівняння не виконується. Перевірка display values не виявляє всі можливі зміни формул або форматування.

Запис не є транзакцією. Помилка під час вставлення, запису, сортування чи flush може залишити часткові зміни. Автоматичного rollback немає. Позначка VERIFIED записується після завершення, але стара позначка не видаляється на початку невдалого запуску.

## 12. Тригери та порядок запуску

Для обліку:

1. Встановити код в окремому Apps Script і заповнити Script Properties.
2. За потреби виконати `exchangeBiginCode()`.
3. Запустити `previewBiginReportSync()`, перевірити лічильники та помилки зіставлення.
4. Запустити `syncBiginReport()` і переглянути таблицю.
5. Запустити `installBiginReportHourlySync()`.

Для базової вигрузки: `syncBiginEvents()`, потім за потреби `installBiginHourlySync()`.

Кожен інсталятор створює time-based trigger `everyHours(1)`, якщо серед видимих йому тригерів немає такого самого handler name. Він не перевіряє фактичний розклад уже наявного тригера і не виправляє його. Інсталятор базової вигрузки не вимагає попередньої успішної синхронізації. Обидва режими можуть мати власні тригери одночасно; їхній спільний lock може спричинити очікування.

Функцій видалення тригерів, автодеплою з GitHub або керування доступами у скрипті немає. Погодинний тригер не означає запуск точно на початку кожної години.

## 13. Журнал і діагностика

Базова вигрузка журналює кількість подій. Режим обліку журналює JSON:

| Поле | Значення |
| --- | --- |
| `fromBigin` | Кількість подій після GUID-фільтра, до виключення відомих ID |
| `linkedExisting` | Кількість запланованих первинних прив'язок |
| `added` | Кількість запланованих нових рядків |
| `missingContacts` | Кількість запитаних унікальних контактів мінус знайдені |
| `preview` | true для попереднього перегляду |

Після фактичного сортування виводиться `Rows moved into date order: N`. Планові лічильники виводяться до запису, тому сам їхній запис у журналі не доводить успіх синхронізації.

Основні причини зупинки: порожні властивості; OAuth/HTTP/JSON помилка; неочікувана структура API; некоректний ID; порушена пагінація; неправильні заголовки; зайнятий P; дубль ID в таблиці; неоднозначний або відсутній збіг для ручного рядка; невалідні дати нової події; неправильний порядок місяців; зміна таблиці під час підготовки; помилки та квоти Google Apps Script.

Діагностуючи збій, відрізняйте етап до запису від частково виконаного запису. Не запускайте базову вигрузку на вкладці обліку як спосіб виправлення.

## 15. Обмеження, які AI-агент не повинен приховувати

- Спеціального правила для назв із «Тоня» немає: вони обробляються як звичайні події.
- Зарплата Тоні, заміни Каріною, об'єднання перетинів AURA/SAKURA не реалізовані.
- Немає фільтра «від вересня», incremental API cursor, webhooks або синхронізації змінених старих подій.
- Однаковий `$u_id` з різними Bigin ID не усуває дубль.
- Ручні рядки без ID можуть блокувати імпорт, хоча ручні значення вже прив'язаних рядків зберігаються.
- Немає окремого відсіву скасованих або all-day подій в обліку.
- Назва без AURA завжди дає Sakura; «обидві зали» як окрема категорія не підтримується.
- Повна вигрузка й облік мають різні правила перезапису; їх не можна ототожнювати.
- Регулярна синхронізація не створює резервних копій; копія передбачена для міграції схеми. Rollback, retry і сповіщення про збій відсутні.

## 16. Правила супроводу для AI-агента

Перед змінами перечитайте актуальні BiginSync.gs і кореневий AGENTS.md. Джерело істини для фактичного функціоналу — код. Не впроваджуйте відсутні бізнес-правила під виглядом документації.

Зберігайте рядкові ID, прихований P, точні заголовки й ручні значення прив'язаних рядків. Не перетворюйте облік на повне переписування. Зміна схеми, ключа зіставлення, тарифної формули чи правил дедуплікації потребує явного опису наслідків для старих даних.

Не додавайте до публічного репозиторію Script Properties, OAuth JSON, токени, ID робочих таблиць або реальні записи клієнтів. Для перевірок використовуйте синтетичні дані.

Під час змін коду перевіряйте щонайменше релевантні сценарії: повторний запуск без нових подій, первинна прив'язка, неоднозначний збіг, ручний рядок без ID, дубль ID, однаковий GUID із різними ID, перехід місяця, сортування зі збереженням ручних колонок, межа тарифу й помилка посеред запису. Самої перевірки синтаксису недостатньо для підтвердження роботи Apps Script API.

Каталог scripts/bigin/ містить серверний Apps Script і документацію. Публікація цих файлів у GitHub не встановлює код в Apps Script і не створює тригери. За інструкціями репозиторію push у main запускає Cloudflare Pages; опублікований каталог сайту — dist/.


## 17. Перехід зі старої схеми та ручні додаткові години

Для вже наявної старої вкладки спочатку встановіть новий код в Apps Script, запустіть `migrateBiginReportColumns()`, потім `previewBiginReportSync()` і `syncBiginReport()`. GitHub-коміт сам не змінює робочу таблицю.

Міграція використовує script lock, розпізнає точну стару схему (14 бізнес-колонок і необов'язковий ID в O), а невідому структуру відхиляє. Для повної нової схеми повторний запуск нічого не змінює. Порожня або відсутня вкладка також не потребує міграції.

Перед структурними змінами створюється повна резервна копія вкладки в тому самому Spreadsheet із назвою backup, часовою міткою та ID аркуша. Назва виводиться в журнал. Копія містить робочі дані й залишається приватною в таблиці; її не можна додавати в GitHub.

Алгоритм: роз'єднати розпізнані місячні заголовки; перемістити стару I після старої J через moveColumns; вставити порожню K; записати нові заголовки A:P; відновити об'єднання місяців A:O; приховати P. Переміщення колонок зберігає їхні дані та використовує механізм Sheets для перенесення формул. Примітки, послуги, інформація й ID зсуваються вправо.

Формули суми на наявних рядках із ID або датою A у форматі dd.MM.yyyy замінюються новою формулою L. Це свідома заміна, включно з вручну перевизначеними сумами таких рядків. Нові рядки одразу отримують цю формулу, а K лишається порожньою. Наступні синхронізації не переписують K і L уже прив'язаних подій. При сортуванні K переміщується разом зі своїм заходом.

Міграція не є транзакцією. При частковій помилці не запускайте її повторно на невідомій проміжній схемі: перевірте стан і використайте створену копію для відновлення. Preview старої схеми повідомляє про необхідність міграції та нічого не змінює.

Нові допоміжні функції: `migrateBiginReportColumns()` — резервна копія й одноразова міграція; `biginAmountFormula_(row)` — єдина формула для нових і мігрованих рядків.

## 18. Перевірки

Запуск: `node scripts/bigin/test-bigin.cjs`. Тести на синтетичних даних перевіряють нову схему, порожні й дробові додаткові години, межу тарифу, ID та первинне зіставлення, збереження даних під час міграції, повторний запуск міграції й запис нових рядків. Використовується модель Apps Script API, а не жива Google-таблиця; поведінку об'єднань, посилань формул та прав доступу потрібно також перевіряти у тестовому Spreadsheet.
